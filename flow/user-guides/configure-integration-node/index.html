    Configure an Integration Node#

    6.0 manageOrchestrator/writeWorkflows One

    Integration nodes perform operations in TheHive or third-party products in TheHive Flow. Each integration node targets one product API and exposes its operations as dedicated actions selected within the node. Integrations tagged Beta were built from the provider's API documentation, not tested against a live environment: check them before using them in production. If you have access to a live environment, help validate the integration and share your feedback with the StrangeBee Support team.

    Products hosted on a private network

    Integration nodes can't reach non-public addresses: the step fails with an egress guard error. To target a product hosted on your internal network, an administrator must first add its address range to the egress allowlist.

    Configure a TheHive integration node#

    A TheHive integration node performs operations in TheHive through TheHive API. It can create, retrieve, update, and delete cases, alerts, tasks, and observables. It can also add, update, and delete comments, create and update task logs, merge an alert into a case, or run a custom query. Each operation is a dedicated action selected within the node. The node can target the local TheHive instance or any other reachable TheHive instance.

    1. Go to the Flow view from the sidebar menu.

    2. Select a workflow from the list.

    3. Drag the previous node connector to an empty area of the canvas.

    4. In the What is the next step? drawer, select Integrations.

    5. Select TheHive.

    6. In the TheHive drawer, enter the following information:

      Variables

      Insert a variable with the $var button, or enter $ and select a variable from the suggestions. To access a field, select the variable to edit its jq expression, or use the + button to insert the variable and the field together.

      Inside the expression, jq functions transform the value before it's inserted in the field. The whole expression stays inside the blue reference, for example:

      • $<node_name>.body.results[0].id: Reads the first identifier of an API response.
      • $<node_name>.body.items | map(.name) | join(", "): Turns a list of objects into a comma-separated text.
      • $<node_name>.body.createdAt / 1000 | todate: Formats a TheHive date, a Unix timestamp in milliseconds, as an ISO 8601 date.
      • $<node_name>.output.title | ascii_upcase: Converts a text to uppercase.

      See Jq Functions for the full list of available functions.

      Fields marked with * are mandatory.

      - Base URL *

      The URL of TheHive instance to call, for example https://<thehive_host>.

      - Authentication *

      In the Authentication section, provide the API key used as a bearer token to authenticate the request.

      - Organization

      The organization the action runs in, sent as the X-Organisation header with every action. If left empty, the action runs in the default organization of the user.

      - Headers

      Extra headers added to every request sent by the node. Select to add a header key and its value.

      Header values are stored in plaintext

      Header values appear in plaintext in the workflow execution history. Reference a secret global variable instead of pasting a credential directly.

      - Action *

      The operation to perform in TheHive. Available actions:

      Family Actions
      Cases Create Case, Get Case, Update Case, Close Case, Delete Case
      Alerts Create Alert, Get Alert, Update Alert, Delete Alert, Merge Alert with Case, Escalate Alert to Case
      Tasks Create Task in Case, Get Task, Update Task, Delete Task
      Observables Create Observable in Case, Create Observable in Alert, Get Observable, Update Observable, Delete Observable
      Comments Create Comment in Case, Create Comment in Alert, Update Comment, Delete Comment
      Attachments Add Attachment to Alert, Add Attachment to Case
      Task Logs Create Task Log, Update Task Log
      Page Templates Create Case Page Template
      Queries Post Query
      Cortex Run Analyzer on Observable, Run Responder

      After you select an action, the drawer displays the fields specific to that action. For the meaning and format of each field, see TheHive API documentation.

      Escalate Alert to Case compared to Merge Alert with Case

      Escalate Alert to Case promotes an alert into a new case. Merge Alert with Case merges an alert into an existing case instead.

      The Cortex actions compared to the Analyzer and Responder nodes

      The Run Analyzer on Observable and Run Responder actions start a Cortex job through TheHive API. Run Analyzer on Observable requires the analyzer, Cortex instance, and observable identifiers. Run Responder requires the responder identifier and the entity's type and identifier. Both return TheHive API response rather than the Cortex report.

      To pick an analyzer or a responder from a list filtered by observable or entity type, and to get the report itself as an output, use the Analyzer or Responder action node instead.

      The Add Attachment to Alert and Add Attachment to Case actions

      The File field takes a file reference produced by an earlier node, such as a file downloaded by an HTTP request action node or uploaded to the Webhook trigger, not literal text content. The field holds one reference and nothing else. Text around the reference or a second reference shows an inline error, because the run would fail. In this field, picking an entry from the Files group of the variable suggestions inserts the file itself, not its metadata.

      - Editor mode

      For actions that send a request body, select how to provide it:

      • Form: Fill in one field per body parameter.
      • Raw: Provide the whole request body in the Request body (raw) field.

      - Query parameters

      Optional query parameters sent with the request, entered as key-value pairs. Select to add a parameter. This section appears only for actions that accept query parameters.

      The Post Query action

      The Post Query action runs a TheHive query: an array of chained operations that search, filter, sort, and paginate data across any entity type. A pipeline starts with a primary operation that defines the initial set of entities. It can then chain a related object operation to navigate to associated entities, filter and sort steps to narrow and order the results, and a page step to paginate. Provide the pipeline in the Query field as a JSON array.

      For example, this query returns the first five in-progress tasks of case ~1234, sorted by due date from earliest to latest, with the assigned case template and the total count:

      [
  {"_name": "getCase", "idOrName": "~1234"},
  {"_name": "tasks"},
  {
    "_name": "filter",
    "_eq": {"_field": "status", "_value": "InProgress"}
  },
  {
    "_name": "sort",
    "_fields": [{"dueDate": "asc"}]
  },
  {
    "_name": "page",
    "from": 0,
    "to": 5,
    "extraData": ["caseTemplate", "total"]
  }
]

      For the full list of operations, filters, and computed fields, see Query and Export in TheHive API documentation.

    7. Optional: Configure the following settings.

      - SSL/TLS

      Configure SSL/TLS settings for secure communication with the external service.

      Use this section when the service relies on a private certificate authority (CA), requires client certificate authentication through mutual TLS, or uses a non-standard trust chain.

      Field Description
      Client certificate (mTLS) Whether the node authenticates with a client certificate (mutual TLS). Do not use a client certificate is the default. Select Provide a client certificate and key to fill in the two fields below.
      Client certificate (PEM) The client certificate to present during the SSL/TLS handshake, in PEM format. Required when Client certificate (mTLS) is Provide a client certificate and key.
      Client certificate key (PEM) The private key associated with the client certificate, in PEM format. Required when Client certificate (mTLS) is Provide a client certificate and key.
      Server verification How the node verifies the identity of the server. Uses the system's pre-installed certificate authorities is the default. Provide a custom CA certificate to verify the server uses the certificate in the next field. Do not verify the server's identity (not recommended for production) exposes the connection to security risks.
      CA certificate (PEM) The CA certificate used to verify the identity of the server, in PEM format. Required when Server verification is set to Provide a custom CA certificate to verify the server.

      - Proxy

      Configure how the node connects to the external service when a proxy is required.

      Select a Proxy mode:

      • Do not use a proxy: No proxy is applied. All requests are sent directly. This is the default.

      • Use the platform default proxy configuration: Uses the global proxy settings defined in TheHive application.conf. See proxy configuration in TheHive.

      • Configure a custom proxy: Defines a custom proxy for this node, overriding the global configuration.

      When Proxy mode is Configure a custom proxy, provide the following information:

      Field Example
      Protocol https
      Address * proxy.example.com
      Port 8080
      Username $global.proxy_user
      Password $secret.proxy_password

      - Error handling

      Configure whether the node fails on error responses.

      By default, the node fails when the response returns a 4xx or 5xx error status code. Turn on Ignore error status codes to make the node succeed regardless of the response status code. Then handle errors in the workflow, for example with an If flow node evaluating the code output. Error responses aren't retried when the option is on.

      Two cases still fail the node:

      • A transport failure, such as a DNS, connection, TLS, or timeout error. The node sets no output.
      • A response announced as JSON that can't be parsed. The node sets the code and headers outputs but no body, and isn't retried.

      When Ignore error status codes is off, the node retries a 408, 429, or 5xx response up to the number of times set in Retry attempts. Any other 4xx response fails the node immediately, without retrying. When the called service includes a Retry-After header in its response, the node waits that long before the next attempt, up to a maximum of 5 minutes. This wait replaces the delay set by Retry delay and Backoff.

    8. Optional: Select Add options to configure the following settings.

      - Timeout & retry

      Configure how the node handles execution time limits and failure recovery.

      If the timeout is reached, the node fails.

      Global timeout vs. local timeout

      A timeout for the entire workflow is defined when creating the workflow. When both a node timeout and a workflow-level timeout are defined, the shortest timeout value applies.

      Field Description
      Timeout Maximum allowed execution time for the node, in seconds, minutes, or hours. The minimum value is 30 seconds.
      Retry attempts Number of times the node is retried on failure.
      Retry delay Time to wait between retry attempts, in seconds, minutes, or hours. Without a delay, retries run 1 second apart by default.
      Backoff Coefficient applied to the retry delay to increase the wait time after each failed attempt.

      Retries and timeouts

      If the node includes retry settings, the timeout applies to each attempt, not to the total duration of all attempts.

      Each request the node sends stops after 30 seconds, even when the node timeout is longer or not set. A response body larger than 10 MiB, the default limit an administrator can change, fails the node without a retry.

      - Execution configuration

      Set the Execution mode to control how the node behaves when several branches converge on it.

      Mode Behavior
      Execute once per branch The node runs once for each incoming branch. Applies when this section isn't configured.
      Wait for all branches The node waits for all incoming branches to complete, then runs once.

    Execution outputs

    When executed, the node returns the following outputs. Each output is a JSON value:

    Output Type Description
    body object The response body returned by TheHive API.
    code number The HTTP status code returned by TheHive.
    headers object The response headers returned by TheHive.

    To access outputs, select your TheHive node and then select in the top-right corner of the screen. Hover over each output name to view its details.

    You can then reuse these outputs as output variables in subsequent nodes. Select the $var button, or enter $ and select the output from the suggestions. Inserted references appear in the following form:

    • $<node_name>.body.<field_name>: to get a value from the response body, for example the identifier of a created case
    • $<node_name>.code: to get the HTTP status code, for example to check whether the request succeeded
    • $<node_name>.headers.<header_name>: to get a specific response header

      Records are addressed by sys_id

      The get, update, replace, and delete actions identify a record by its sys_id, a 32-character identifier, not by its number such as INC0010001. To resolve a number to a sys_id, use the matching list or search action with an encoded query. In Query parameters, add a parameter named sysparm_query with a value such as number=INC0010001.       - Error handling

      Configure whether the node fails on error responses.

      By default, the node fails when the response returns a 4xx or 5xx error status code. Turn on Ignore error status codes to make the node succeed regardless of the response status code. Then handle errors in the workflow, for example with an If flow node evaluating the code output. Error responses aren't retried when the option is on.

      Two cases still fail the node:

      • A transport failure, such as a DNS, connection, TLS, or timeout error. The node sets no output.
      • A response announced as JSON that can't be parsed. The node sets the code and headers outputs but no body, and isn't retried.

      When Ignore error status codes is off, the node retries a 408, 429, or 5xx response up to the number of times set in Retry attempts. Any other 4xx response fails the node immediately, without retrying. When the called service includes a Retry-After header in its response, the node waits that long before the next attempt, up to a maximum of 5 minutes. This wait replaces the delay set by Retry delay and Backoff.

    8. Optional: Select Add options to configure the following settings.

      - Timeout & retry

      Configure how the node handles execution time limits and failure recovery.

      If the timeout is reached, the node fails.

      Global timeout vs. local timeout

      A timeout for the entire workflow is defined when creating the workflow. When both a node timeout and a workflow-level timeout are defined, the shortest timeout value applies.

      Field Description
      Timeout Maximum allowed execution time for the node, in seconds, minutes, or hours. The minimum value is 30 seconds.
      Retry attempts Number of times the node is retried on failure.
      Retry delay Time to wait between retry attempts, in seconds, minutes, or hours. Without a delay, retries run 1 second apart by default.
      Backoff Coefficient applied to the retry delay to increase the wait time after each failed attempt.

      Retries and timeouts

      If the node includes retry settings, the timeout applies to each attempt, not to the total duration of all attempts.

      Each request the node sends stops after 30 seconds, even when the node timeout is longer or not set. A response body larger than 10 MiB, the default limit an administrator can change, fails the node without a retry.

      Set the Execution mode to control how the node behaves when several branches converge on it.

      Mode Behavior
      Execute once per branch The node runs once for each incoming branch. Applies when this section isn't configured.
      Wait for all branches The node waits for all incoming branches to complete, then runs once.

      CA certificate (PEM) The CA certificate used to verify the identity of the server, in PEM format. Required when Server verification is set to Provide a custom CA certificate to verify the server.

      - Error handling

      Configure whether the node fails on error responses.

      By default, the node fails when the response returns a 4xx or 5xx error status code. Turn on Ignore error status codes to make the node succeed regardless of the response status code. Then handle errors in the workflow, for example with an If flow node evaluating the code output. Error responses aren't retried when the option is on.

      Two cases still fail the node:

      • A transport failure, such as a DNS, connection, TLS, or timeout error. The node sets no output.
      • A response announced as JSON that can't be parsed. The node sets the code and headers outputs but no body, and isn't retried.

      When Ignore error status codes is off, the node retries a 408, 429, or 5xx response up to the number of times set in Retry attempts. Any other 4xx response fails the node immediately, without retrying. When the called service includes a Retry-After header in its response, the node waits that long before the next attempt, up to a maximum of 5 minutes. This wait replaces the delay set by Retry delay and Backoff.

      - Timeout & retry

      Configure how the node handles execution time limits and failure recovery.

      If the timeout is reached, the node fails.

      Global timeout vs. local timeout

      A timeout for the entire workflow is defined when creating the workflow. When both a node timeout and a workflow-level timeout are defined, the shortest timeout value applies.

      Field Description
      Timeout Maximum allowed execution time for the node, in seconds, minutes, or hours. The minimum value is 30 seconds.
      Retry attempts Number of times the node is retried on failure.
      Retry delay Time to wait between retry attempts, in seconds, minutes, or hours. Without a delay, retries run 1 second apart by default.
      Backoff Coefficient applied to the retry delay to increase the wait time after each failed attempt.

      If the node includes retry settings, the timeout applies to each attempt, not to the total duration of all attempts.

      Each request the node sends stops after 30 seconds, even when the node timeout is longer or not set. A response body larger than 10 MiB, the default limit an administrator can change, fails the node without a retry.

      Set the Execution mode to control how the node behaves when several branches converge on it.

      Mode Behavior

    Configure a Wazuh integration node#

    A Wazuh integration node runs operations against the Wazuh server API. It can list, add, restart, and delete agents, assign agents to groups, run active responses, and run file integrity monitoring scans. It can also read file integrity monitoring findings, security configuration assessment results, rules, CDB lists, manager status and logs, and task status. Each operation is a dedicated action selected within the node.

    1. Go to the Flow view from the sidebar menu.

    2. Select a workflow from the list.

    3. Drag the previous node connector to an empty area of the canvas.

    4. In the What is the next step? drawer, select Integrations.

    5. Select Wazuh.

    6. In the Wazuh drawer, enter the following information:

      Variables

      Insert a variable with the $var button, or enter $ and select a variable from the suggestions. To access a field, select the variable to edit its jq expression, or use the + button to insert the variable and the field together.

      Inside the expression, jq functions transform the value before it's inserted in the field. The whole expression stays inside the blue reference, for example:

      • $<node_name>.body.results[0].id: Reads the first identifier of an API response.
      • $<node_name>.body.items | map(.name) | join(", "): Turns a list of objects into a comma-separated text.
      • $<node_name>.body.createdAt / 1000 | todate: Formats a TheHive date, a Unix timestamp in milliseconds, as an ISO 8601 date.
      • $<node_name>.output.title | ascii_upcase: Converts a text to uppercase.

      See Jq Functions for the full list of available functions.

      Fields marked with * are mandatory.

      - Base URL *

      The URL of your Wazuh server API, for example https://<wazuh_server>:55000.

      - Authentication *

      In the Authentication section, select the Authentication method and provide its credentials. The Wazuh node supports two methods:

      Authentication method Fields
      basic_auth Username *, Password
      bearer_token Bearer token *

      The Wazuh server API accepts a username and password only to issue a token. Use basic_auth with the Authenticate action, and bearer_token with every other action. In the Bearer token field, insert the body.data.token output of the Authenticate node with the $var button. By default, a token expires after 900 seconds. Reference secret global variables instead of pasting credentials directly.

      - Headers

      Extra headers added to every request sent by the node. Select to add a header key and its value.

      Header values are stored in plaintext

      Header values appear in plaintext in the workflow execution history. Reference a secret global variable instead of pasting a credential directly.

      - Action *

      The operation to perform in Wazuh. Available actions:

      Family Actions
      Authentication Authenticate
      Agents List Agents, Add Agent, Insert Agent with ID and Key, Delete Agents, Get Agent Key, Restart Agent, Get Agents Status Summary, Assign Agent to Group
      Active Response Run Active Response
      File Integrity Monitoring Get FIM Findings, Run FIM Scan
      Security Configuration Assessment Get SCA Results, Get SCA Policy Checks
      Rules Get Rules
      CDB Lists Get CDB Lists, Get CDB List File
      Manager Get Manager Status, Get Manager Logs
      Tasks List Tasks Status

      After you select an action, the drawer displays the fields specific to that action. For the meaning and format of each field, see the Wazuh server API reference.

      The Run Active Response action

      The Command field takes the name of a command declared in a <command> block of the manager ossec.conf file. To call an active response script by its file name instead, prefix it with !, for example !firewall-drop. Enter the target IP address in the Source IP field for firewall-drop, host-deny, route-null, and netsh, and the target user account in the Target User field for disable-account.

      Failures on agents return a 200 status code

      Delete Agents, Restart Agent, Run Active Response, and Run FIM Scan return a 200 status code even when the operation fails for some or all agents. Check body.error in a later node: 0 means done, 1 failed, and 2 partial. The agents the operation failed on are listed in body.data.failed_items.

      - Editor mode

      For actions that send a request body, select how to provide it:

      • Form: Fill in one field per body parameter.
      • Raw: Provide the whole request body in the Request body (raw) field.

      - Query parameters

      Query parameters sent with the request, entered as key-value pairs. Select to add a parameter. This section appears only for actions that accept query parameters.

      The following actions require query parameters. Add each one with the name listed, or the node fails:

      • Delete Agents: agents_list and status
      • Run Active Response: agents_list

      agents_list takes a comma-separated list of agent IDs, such as 003,004. Without it, Run Active Response would run the command on every agent.

      • Configure a custom proxy: Defines a custom proxy for this node, overriding the global configuration.
